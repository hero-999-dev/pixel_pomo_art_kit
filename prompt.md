# Recreation Prompt — Pixel Pomo Art Kit

**Version 1 — 2026-07-25.** Written once the app was feature-complete, so it
describes what the app actually does rather than what was planned. Keep it
updated whenever the app's real behaviour changes.

Paste the prompt below into a fresh AI chat, or hand it to a developer, to
rebuild the Pixel Pomo Art Kit from nothing.

## The prompt

> Build a Windows desktop app called **Pixel Pomo Art Kit**: a companion
> pixel-art editor for a separate game called **Pixel Pomo**, specifically for
> drawing the flower sprites in its garden feature. The game keeps its sprites
> as a 16-cell-wide grid of palette letters, generated by a Python module
> called `gen_objects.py`. The whole point of the editor is that what it
> exports is **byte-for-byte identical** to what the game ships — not an
> approximation, not a reimplementation, the literal same bytes — achieved by
> importing and calling the game's own generator code for every preview and
> every export, rather than duplicating its logic in the editor.
>
> ### Document model (a pure module, no UI code, no file I/O)
> - A `Palette`: nine hex-string slots (`d`/`m`/`l` dark/mid/light petal
>   tones, a `centre`, a bloom-outline `rim`, a `plant_rim`, plus stem/leaf/
>   vein greens shared across every flower) resolving to RGBA tuples. Two of
>   the nine (a bloom seam colour and a plant seam colour) are derived from
>   `rim`/`plant_rim` rather than stored a second time, since the generator
>   reuses the outline colour for interior seams too.
> - A `Drawing`: a name, a species id, a model index, a `Palette`, and a grid
>   of cells where each cell is empty, a palette letter, or a raw `(r,g,b,a)`
>   tuple from a free colour picker. A drawing's kind is "letters" while every
>   non-empty cell is a letter, and flips to "pixels" the moment any cell
>   holds a raw tuple — one grid holds both, rather than a separate "pixel
>   mode" with its own document format.
> - A `History`: undo/redo as whole-grid snapshots grouped by stroke (a
>   begin/end pair brackets a drag so the whole drag is one undo step, not one
>   per cell touched), capped at a couple hundred entries, with the redo
>   branch dropped the moment a new stroke follows an undo.
>
> ### The bridge to the game
> - Import the game's `gen_objects.py` by file path — overridable by an
>   environment variable so the editor isn't hard-wired to one checkout — and
>   cache it after the first load.
> - A closed catalogue of the game's flower species. Load each shipped model
>   as an editable drawing: read its letter grid and palette straight out of
>   the generator's own data tables for most species. The one species whose
>   sprite is stored as already-composited raw pixels rather than a letter
>   grid should import as a "pixels"-kind drawing instead — still fully
>   editable, still exportable, just never eligible to become a grid literal
>   (see below).
> - A `render(drawing)` function: turn a drawing into the actual RGBA grid the
>   game would draw. Split the cells into their two material layers (the
>   coloured "bloom" and the green "plant" parts), outline each layer in its
>   own rim colour using the generator's real outlining function, composite
>   any raw-colour cells on top untouched, and combine the layers with the
>   generator's own compositing function. Both the live canvas preview and
>   every raster export must call this one function, so the preview can never
>   show something an export would disagree with.
> - Exports, each calling the generator's real scaling/writing code so the
>   output bytes match what the game's own asset pipeline would produce:
>   - **PNG** at a chosen scale.
>   - **JPG** — the same render flattened onto a caller-supplied background
>     colour, since JPEG has no alpha channel; report which colour was used
>     rather than silently picking one.
>   - **The actual shipped sprite file(s)**, named the way the game's asset
>     folder expects. Refuse a drawing that isn't exactly 16 cells wide, or
>     has no species chosen yet. Exporting a drawing's first model should also
>     write the second file the game uses as a shop thumbnail.
>   - **A grid literal**: the drawing's rows as source-code text, ready to
>     paste back into the generator's own letter-grid table. Refuse this one
>     outright — don't approximate it — the moment a single cell holds a raw
>     colour, since there is no letter to write down for it.
>   - One dedicated exception type covering every refusal above, so the UI can
>     show the artist a plain explanation instead of a stack trace.
>
> ### Storage
> - One drawing per file, JSON, human-readable and hand-editable on purpose —
>   a row of letters should serialise as one plain string, not one JSON value
>   per cell.
> - Make saves atomic: serialise fully in memory first, write to a sibling
>   temp file, then a single rename into place — a save that dies partway
>   through must never corrupt the previously-good file.
> - Validate hard on load: an unknown letter, a wrong-length colour tuple, a
>   ragged grid, a row that's neither a string nor a proper list, or an
>   unrecognised kind should all raise one dedicated "this file is corrupt"
>   exception rather than letting a raw `KeyError`/`TypeError`/`IndexError`
>   escape to the caller.
> - A library over a folder of these files: load everything, returning the
>   paths it had to skip rather than raising, so one bad file doesn't take
>   down the rest; add/save/remove/duplicate drawings by object identity,
>   never by value-equality (two blank drawings can be equal without being
>   the *same* drawing, and removing "the" one that matches by value can
>   delete the wrong one); and seed the folder from the game's shipped
>   flowers exactly once — a no-op if anything is already in there.
>
> ### The window (three panes)
> - A scrollable **library** list on the left: a small thumbnail, the
>   drawing's name, and a menu for duplicate / export PNG / export JPG /
>   export engine sprite / copy grid literal / rename / delete, plus a button
>   to start a new blank drawing that carries over the currently open
>   drawing's species and palette.
> - An expanding **canvas** in the centre: click or drag to paint with the
>   current tool and ink, interpolating between sparse drag events so a fast
>   stroke stays a continuous line; right-click as an eyedropper that makes
>   the cell under the cursor the current ink; mouse wheel (or `+`/`-`) to
>   zoom, with scrollbars so edge cells stay reachable at maximum zoom; a
>   checkerboard under transparent cells; grid lines once zoomed in enough to
>   show them usefully. Beside it, two small live previews rendered through
>   the exact same code as every export — one at actual size, one at a fixed
>   "squint test" scale so the artist can sanity-check readability without
>   eyeballing a zoom level themselves.
> - A **tools** pane on the right: draw / erase / flood-fill tools plus a
>   mirror-X toggle that composes with all three (flowers are symmetric —
>   half the clicks), undo/redo, a swatch that always shows what the next
>   click will paint, one button per palette letter coloured from the open
>   drawing's own palette (the active letter visibly pressed; right-clicking
>   a slot recolours that palette entry for the whole drawing — palette edits
>   apply to every undo snapshot rather than being undoable strokes), a row
>   of app-wide ready-made colours, and a free colour picker for anything
>   else.
> - Library rows also offer: naming a drawing's species (validated to the
>   engine's lowercase id form — this is what unlocks engine export for a
>   brand-new flower), changing its row count (width is the engine's fixed
>   16; a resize is one undoable stroke), and copying the palette as a
>   `_FLOWER_PALS` source line to pair with the grid literal.
> - The library keeps a `.bak` of each file as it was when the session first
>   touched it — the rescue that survives closing the window.
> - Split the pointer handling in two layers: methods that take grid
>   coordinates and carry all of the actual behaviour (paint, erase, begin/end
>   a stroke) versus the toolkit's own event bindings, which do nothing but
>   convert a pixel position into a cell and call those methods. That split is
>   what lets the interaction be unit-tested without ever opening a window.
> - Standard keyboard shortcuts for undo, redo, tool switching, and zoom.
> - The entry point opens the window at a reasonable default size, backed by
>   a library folder that seeds itself from the game's shipped flowers on
>   first run, and warns — without failing to start — if any saved file on
>   disk couldn't be read.
>
> ### Testing
> - Plain standard-library test framework, no external dependency for testing
>   itself. Nothing should need a display except the window's own smoke
>   tests, and those should skip themselves cleanly — not fail — when no
>   display is available.
> - Treat the render/export path as correct only once it's proven against the
>   game's real generator output byte-for-byte, not merely "looks right" in a
>   screenshot. That comparison is the one test that actually defends the
>   whole reason the app exists.
> - Cover the data model's edges (undo past the start, redo past the end, a
>   stroke that changed nothing, the undo cap), the storage layer's
>   corruption handling, and the window wired up end-to-end through the same
>   grid-coordinate methods the rest of the suite calls directly.
